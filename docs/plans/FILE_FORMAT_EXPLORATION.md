# 인물 데이터 전달·압축 검토

> **검토안 — 확정된 계획이나 구현 사양이 아니다.** 아래 형식, 확장자, 압축 방식과 적용 시점은 추후 호환성 및 실제 데이터 크기를 확인한 뒤 결정한다. 현재 구현된 JSON v1 저장·불러오기 동작을 변경하는 문서는 아니다.

## 목적과 전제

- 포즈·비율·색상 등을 다른 인물에 선택적으로 적용할 수 있도록 데이터를 전달한다.
- 다른 범용 앱은 데이터의 의미를 해석할 필요가 없다. 메신저·메모 앱 등을 통해 파일이나 텍스트를 전달할 수 있으면 된다.
- 전용 파일 저장과 클립보드 복사·붙여넣기는 별도 전달 방식으로 검토한다.
- 인물 전체 저장과 자유 도형·텍스처는 향후 기능이며 현재 이 문서에서 구현을 확정하지 않는다.

## 외부 파일 참조 가능성

텍스처 등 실제 파일은 인물 데이터와 별도로 보관·전달하고, 인물 데이터에는 필요한 파일의 식별자와 이름 같은 참조 정보만 기록하는 방안을 검토한다. 운영체제나 기기마다 달라지는 절대 경로에 의존하지 않는다.

불러올 때 필요한 파일이 없으면 누락된 파일을 알리고 사용자가 나중에 연결할 수 있어야 한다. 참조만으로 실제 파일의 복원이 보장되지는 않으므로, 공유할 때 외부 파일을 함께 전달해야 한다. 파일 식별 방식, 동일 이름 충돌, 내용 변경 확인 및 재연결 UI는 추후 결정한다.

## 압축·전달 방식 후보

1. **전용 파일:** 인물 데이터를 JSON 등으로 직렬화하고 gzip 같은 무손실 압축으로 저장하는 바이너리 파일. 전용 확장자는 형식 식별을 돕지만 확장자 자체가 압축을 수행하지는 않는다.
2. **클립보드 텍스트:** 같은 데이터를 압축한 뒤 Base64로 인코딩하여 텍스트로 전달하는 방식. 형식·버전을 식별할 접두어를 둘 수 있다. Base64는 압축된 바이너리보다 길어지며, 텍스트로 전달할 수 있다는 뜻이지 다른 앱이 포즈를 해석할 수 있다는 뜻은 아니다.
3. **비압축 JSON:** 작은 데이터의 단순성과 점검 가능성이 중요할 때의 대안. 공백 없는 JSON을 복사하고, 사람이 읽는 파일에는 들여쓰기를 사용할 수 있다.

위 후보를 함께 지원할지, 한 방식만 사용할지 또는 크기에 따라 선택할지는 미정이다. 기존 JSON v1 불러오기와의 호환성 및 새 형식의 버전·압축 방식 식별도 함께 검토해야 한다.

## 현재 크기 참고 측정

2026-10-17 기준 기본 리그와 현재 JSON v1 프리셋을 `JSON.stringify`로 공백 없이 직렬화하고, UTF-8 바이트에 gzip을 적용해 측정했다. Base64는 gzip 결과만 인코딩했으며 식별 접두어는 포함하지 않았다. 이 표의 JSON은 ASCII만 포함해 문자 수와 UTF-8 바이트 수가 같았다.

| 데이터 | JSON 문자 수 | gzip 바이트 | gzip + Base64 문자 수 |
|---|---:|---:|---:|
| 포즈 | 1,362 | 348 | 464 |
| 비율 | 764 | 282 | 376 |
| 색상 | 725 | 296 | 396 |
| 전체 | 2,691 | 594 | 792 |

기본 인물의 단일 측정값일 뿐 크기 보장치는 아니다. 편집된 좌표의 정밀도, 팔레트, 도형 수, 참조 파일 이름 및 향후 스키마에 따라 달라진다. 실제 텍스처 파일의 크기는 포함하지 않았다. 형식 결정 전에는 대표적인 실제 작업 데이터로 다시 측정한다.

## 추가 검토 사항

- 포즈만 적용할 때 대상 인물의 관절 간 거리와 비율을 어떻게 보존할지 먼저 정의하고 검증한다.
- 압축 해제 후 크기 제한과 데이터 검증, 손상된 데이터 및 지원하지 않는 버전의 오류 처리를 설계한다.
- 대상 브라우저의 압축·클립보드 지원과 권한 제한, 미지원 환경의 대체 방법을 확인한다.
- 외부 파일 참조에 민감한 로컬 경로나 불필요한 개인정보가 포함되지 않도록 한다.
- 사용자에게 데이터 파일과 별도 에셋을 함께 전달해야 한다는 점을 명확히 안내한다.
